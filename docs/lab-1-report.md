# Личный отчёт по лабораторной работе №1

Дата выполнения: 21.09.2026
Дисциплина: «Технологии нагруженных систем обработки данных»

## 1. Цель работы

Разработать доменный сервис `UserService`, который предоставляет CRUD-операции над пользователями через gRPC и хранит данные в PostgreSQL.

Сервис должен поддерживать:

- создание пользователя с проверкой уникальности логина;
- получение пользователя по идентификатору;
- получение пользователей по имени и фамилии;
- изменение всех полей, кроме идентификатора и логина;
- удаление пользователя по идентификатору.

## 2. Результат

Реализован работающий gRPC-сервис с трёхслойной архитектурой, PostgreSQL, Dapper, Mapperly и FluentValidation. Пароли не сохраняются в открытом виде: в БД записываются PBKDF2-хеш и случайная соль.

Код лабораторной находится в каталоге `UserService`, автоматические тесты — в `UserService.Tests`.

## 3. Архитектура

Внутри одного проекта сервис разделён по папкам на уровни:

```text
UserService/
├── Api/
│   ├── Configuration/
│   ├── Interceptors/
│   ├── Mappers/
│   ├── Services/
│   └── Validators/
├── Application/
│   ├── Abstractions/
│   ├── Exceptions/
│   ├── Models/
│   └── Services/
├── Domain/
│   └── Entity/
├── Infrastructure/
│   ├── Database/
│   ├── Mappers/
│   ├── Models/
│   └── Repositories/
├── Protos/
├── Program.cs
└── UserService.csproj
```

Поток обработки запроса:

```text
gRPC request
    → FluentValidation
    → UserGrpcService
    → Application UserService
    → IUserRepository / UserRepository
    → Dapper
    → PostgreSQL function
```

### Ответственность уровней

- `Api` принимает gRPC-запросы, выполняет структурную валидацию, преобразует контракты и формирует gRPC-ответы.
- `Application` содержит бизнес-логику, модели команд и абстракции зависимостей.
- `Domain` содержит доменную сущность пользователя.
- `Infrastructure` отвечает за PostgreSQL, Dapper, DB-модели и преобразование данных.

## 4. Доменная модель

Сущность пользователя содержит:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `Id` | `int` | Идентификатор пользователя |
| `Login` | `string` | Уникальный логин |
| `PasswordHash` | `string` | Хеш пароля |
| `PasswordSalt` | `string` | Соль для хеширования |
| `Name` | `string` | Имя |
| `Surname` | `string` | Фамилия |
| `Age` | `int` | Возраст |

Внешний gRPC-ответ не содержит хеш и соль пароля.

## 5. gRPC API

Контракт расположен в `UserService/Protos/user-service.proto`.

| Метод | Вход | Результат |
| --- | --- | --- |
| `CreateUser` | логин, пароль, имя, фамилия, возраст | созданный пользователь |
| `GetUserById` | идентификатор | один пользователь |
| `GetUserByName` | имя и фамилия | массив найденных пользователей |
| `UpdateUser` | идентификатор и изменяемые поля | обновлённый пользователь |
| `DeleteUser` | идентификатор | пустой успешный ответ |

В `UpdateUserRequest` изменяемые поля объявлены как `optional`. Это позволяет отличить отсутствующее значение от явного `age = 0`.

## 6. Работа с PostgreSQL

### Таблица

Таблица `users` создаётся отдельным скриптом. Для `login` задано ограничение `UNIQUE`, а для возраста — проверка диапазона от 0 до 150.

### Индексы

- уникальный индекс по `login` создаётся ограничением `UNIQUE`;
- составной индекс `idx_users_full_name` создан по `(name, surname)` для метода `GetUserByName`.

### Функции

Каждая операция вынесена в отдельную функцию:

- `exists_user_by_login`;
- `create_user`;
- `get_user_by_id`;
- `get_user_by_name`;
- `update_user`;
- `delete_user`.

Скрипты таблицы, индекса и функций хранятся раздельно в `Infrastructure/Database` и автоматически применяются при первом запуске контейнера PostgreSQL.

### Dapper

Репозиторий открывает соединение через `NpgsqlDataSource`, вызывает функции по имени и передаёт параметры через `DynamicParameters`. Во все операции передаётся `CancellationToken`.

Метод поиска по имени возвращает `User[]`, поскольку несколько пользователей могут иметь одинаковые имя и фамилию.

## 7. Валидация

Структурная валидация выполняется синхронными FluentValidation-валидаторами на уровне API:

- обязательность логина, пароля, имени и фамилии;
- максимальная длина строковых полей БД — 100 символов;
- возраст от 0 до 150;
- положительный идентификатор;
- наличие хотя бы одного изменяемого поля в `UpdateUser`.

Проверка уникальности логина является бизнес-правилом и выполняется в application-сервисе.

## 8. Обработка ошибок

`GrpcExceptionInterceptor` преобразует исключения в gRPC-статусы:

| Ситуация | gRPC status |
| --- | --- |
| Некорректный запрос | `InvalidArgument` |
| Логин уже существует | `AlreadyExists` |
| Пользователь не найден | `NotFound` |
| Запрос отменён | `Cancelled` |
| Необработанная ошибка | `Internal` |

Необработанные исключения логируются, а внутренние детали не возвращаются клиенту.

## 9. Хеширование паролей

Для паролей используется PBKDF2-HMAC-SHA256:

- соль: 16 байт;
- ключ: 32 байта;
- количество итераций: 100 000;
- сравнение хешей: `CryptographicOperations.FixedTimeEquals`.

В БД и ответах API открытый пароль отсутствует.

## 10. Dependency Injection

Stateless-компоненты зарегистрированы как singleton:

- application-сервис;
- репозиторий;
- хешировщик;
- Mapperly-мапперы;
- FluentValidation-валидаторы;
- interceptor;
- `NpgsqlDataSource`.

Настройки PostgreSQL читаются через `IOptions<PostgresOptions>` и проверяются при старте приложения.

## 11. Тестирование

Автоматические тесты проверяют:

- хеширование пароля перед сохранением;
- запрет повторного логина;
- получение одного пользователя и массива однофамильцев;
- ошибки при отсутствии пользователя;
- частичное обновление полей;
- успешное и неуспешное удаление;
- структурные валидаторы;
- корректную обработку `optional`-полей;
- отсутствие пароля в API-ответе;
- Mapperly-маппинг контрактов.

Итоговый запуск: 19 тестов, 19 успешно, 0 ошибок.

Дополнительно выполнен интеграционный smoke-тест с реальными PostgreSQL и gRPC:

1. Созданы два пользователя с одинаковыми именем и фамилией.
2. `GetUserByName` вернул обоих пользователей.
3. `GetUserById` вернул пользователя по идентификатору.
4. `UpdateUser` изменил только переданные поля.
5. Повторный логин вернул `AlreadyExists`.
6. Невалидные данные вернули `InvalidArgument`.
7. После удаления запрос по идентификатору вернул `NotFound`.
8. Проверено, что в PostgreSQL хранится хеш, а не открытый пароль.

## 12. Запуск проекта

```powershell
cd .\UserService
docker compose up -d --wait
cd ..
dotnet restore .\RateLimiter.sln
dotnet run --project .\UserService\UserService.csproj
```

Адрес сервиса: `http://localhost:5002`. Для запросов из Postman нужно импортировать `UserService/Protos/user-service.proto`.

Запуск тестов:

```powershell
dotnet test .\UserService.Tests\UserService.Tests.csproj -c Release
```

Остановка PostgreSQL без удаления данных:

```powershell
cd .\UserService
docker compose down
```
