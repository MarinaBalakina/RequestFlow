
# RequestFlow — система контроля пользовательских запросов 

## О проекте

**RequestFlow** — это backend-система на C# и .NET, которая позволяет управлять пользователями и контролировать частоту их обращений к API.

Основная задача проекта — ограничение нагрузки на отдельные методы сервиса. Система отслеживает активность пользователей, проверяет количество запросов и временно ограничивает доступ при превышении установленного лимита.

Например, если для определённого метода разрешено не более 10 запросов в минуту, пользователь, превысивший это ограничение, теряет доступ к данному методу на 5 минут. При этом остальные пользователи продолжают работать с системой.

Ограничения можно изменять во время работы приложения без перезапуска сервисов.

---

# Архитектура системы

Проект построен на микросервисной архитектуре. Каждый сервис отвечает за отдельную часть системы.

### UserService

Отвечает за работу с пользователями:

- создание и удаление пользователей;
- поиск и обновление пользовательских данных;
- проверку возможности выполнения запроса.

### RateLimiter.Writer

Отвечает за управление ограничениями:

- создание новых правил;
- изменение допустимого количества запросов;
- получение и удаление ограничений.

### RateLimiter.Reader

Отвечает за контроль пользовательской активности:

- получение актуальных ограничений;
- обработку событий из Kafka;
- подсчёт количества запросов;
- временную блокировку пользователей через Redis.

Такое разделение позволяет отделить работу с пользовательскими данными от процессов контроля нагрузки и управления ограничениями.

---

# Работа с пользователями и PostgreSQL

Для хранения пользовательских данных используется **PostgreSQL**.

Система поддерживает основные CRUD-операции: создание, получение, обновление и удаление пользователей. Поиск доступен как по идентификатору, так и по имени и фамилии.

Для взаимодействия с базой данных используются **Dapper и Npgsql**.

SQL-логика вынесена в отдельные функции, которые вызываются из репозиториев. Для передачи параметров используется DynamicParameters.

При проектировании базы данных были предусмотрены:

- уникальность логина пользователя;
- индексы для ускорения поиска;
- ограничения на корректность хранимых данных;
- отдельные SQL-скрипты для создания таблиц, индексов и функций.

Пароли пользователей не хранятся в открытом виде. Перед сохранением они хешируются с использованием PBKDF2 и индивидуальной соли.

# Взаимодействие с системой через gRPC

Для взаимодействия с сервисами реализован **gRPC API**.

В отличие от REST API, gRPC использует заранее описанные контракты в `.proto`-файлах.

В контрактах определяется:

- какие методы предоставляет сервис;
- какие данные необходимо передать в запросе;
- какие данные возвращаются в ответе.

Для передачи данных используется бинарный формат **Protocol Buffers**, который позволяет уменьшить объём передаваемой информации.

В рамках проекта через gRPC выполняются операции с пользователями, управление ограничениями и получение текущих правил, загруженных в память Reader.

---

# Управление ограничениями

## Хранение правил в MongoDB

Для каждого метода UserService можно установить собственное ограничение по количеству запросов в минуту — RPM (Requests Per Minute).

Каждое правило содержит название метода и допустимое количество запросов.

Например:

| Метод | Допустимое количество запросов |
| --- | --- |
| GetUserById | 100 в минуту |
| CreateUser | 10 в минуту |
| UpdateUser | 20 в минуту |

Для хранения этих правил используется **MongoDB**.

Сервис Writer позволяет создавать и изменять ограничения через gRPC API. Для работы с базой данных используется библиотека MongoDB.Driver.

Для названия метода предусмотрен уникальный индекс, поэтому система не позволяет создать несколько правил для одного и того же метода.

---

## Кеширование и обновление ограничений

Поскольку проверка лимитов выполняется при обработке каждого события о запросе, постоянное обращение к MongoDB создавало бы дополнительную нагрузку на базу данных.

Для решения этой задачи в Reader реализован кеш ограничений в памяти.

При запуске сервис загружает данные из MongoDB порциями по 1000 записей и сохраняет их в потокобезопасной коллекции **ConcurrentDictionary**.

Однако возникает другая задача: если ограничение было изменено, данные в памяти сервиса также должны обновиться.

Для этого используется механизм **MongoDB Change Streams**, который позволяет подписаться на изменения в базе данных.

Процесс выглядит следующим образом:

1. Через Writer изменяется ограничение.
2. Новое значение сохраняется в MongoDB.
3. Reader получает информацию об изменении.
4. Ограничение обновляется в кеше.

Таким образом, новые правила начинают применяться при обработке следующих событий без перезапуска приложения.

Для MongoDB без поддержки Change Streams предусмотрен альтернативный механизм периодической синхронизации.

# Асинхронная обработка событий через Apache Kafka

Для передачи и обработки информации о пользовательских запросах используется **Apache Kafka**.

Вместо того чтобы выполнять подсчёт запросов непосредственно внутри UserService, обработка событий вынесена в отдельный сервис Reader.

Это позволяет разделить выполнение пользовательских операций и контроль частоты запросов.

Для взаимодействия с Kafka используется библиотека **Confluent.Kafka**.

## Генерация пользовательской нагрузки

Для моделирования активности пользователей реализовано отдельное консольное приложение на C#.

Оно выступает в роли Producer — отправителя сообщений в Kafka.

Каждое событие содержит:

- `user_id` — идентификатор пользователя;
- `endpoint` — метод, к которому обращается пользователь.

Генератор позволяет одновременно моделировать активность нескольких пользователей с различной частотой запросов.

Например, один пользователь может выполнять 5 запросов в минуту, а другой — 100 запросов к тому же методу.

Параметры генерации можно изменять во время работы приложения: добавлять новых пользователей, изменять частоту запросов и выбирать другие методы.

В текущей версии проекта события о запросах создаются генератором, который имитирует пользовательскую нагрузку.

---

## Получение и обработка событий

Reader выступает в роли Consumer — получателя сообщений из Kafka.

Он получает события и передаёт их в отдельный сервис, который отвечает за подсчёт запросов и проверку ограничений.

Для подсчёта используется алгоритм **Sliding Window (скользящее окно)**.

Система учитывает запросы, выполненные за последние 60 секунд. Более старые события перестают учитываться.

При этом количество запросов рассчитывается отдельно для каждого пользователя и каждого метода.

Также реализована обработка ошибок при получении сообщений. Позиция обработанного сообщения (offset) подтверждается после завершения обработки, а идентификатор события используется для защиты от повторного подсчёта в пределах текущего окна.

---

# Временная блокировка пользователей через Redis

Когда количество запросов превышает установленное ограничение, необходимо сохранить информацию о блокировке пользователя.

Для этой задачи используется **Redis** — быстрое хранилище данных, к которому могут обращаться Reader и UserService.

При превышении лимита Reader создаёт в Redis ключ, содержащий идентификатор пользователя и название метода.

Для ключа устанавливается **TTL (Time To Live)** — время жизни, равное 5 минутам.

После истечения этого времени Redis автоматически удаляет ключ, и пользователь снова получает возможность обращаться к методу.

Например, если пользователь превысил ограничение для GetUserById, это не мешает ему обращаться к другим методам, для которых лимит не был превышен.

Для работы с Redis используется библиотека StackExchange.Redis.

Redis в данном проекте позволяет хранить временные блокировки без необходимости самостоятельно отслеживать время их окончания и удалять устаревшие записи.

# Проверка запросов через gRPC Interceptors

Чтобы заблокированный пользователь не мог выполнить операцию, проверка должна происходить до выполнения основной бизнес-логики UserService.

Для этого используются **gRPC Interceptors** — перехватчики, которые позволяют обрабатывать запросы до их передачи в основной сервис.

В проекте реализовано несколько перехватчиков.

### IdInterceptor

Проверяет наличие и корректность идентификатора пользователя в заголовках запроса.

Если идентификатор отсутствует или имеет некорректное значение, запрос отклоняется.

В текущей реализации проверяется идентификатор из заголовка, а не личность пользователя через полноценную систему аутентификации.

### RateLimitInterceptor

Проверяет наличие временной блокировки пользователя в Redis.

Если пользователь превысил лимит для запрашиваемого метода, выполнение операции прекращается.

Если блокировка отсутствует, запрос передаётся в основной сервис.

### GrpcExceptionInterceptor

Отвечает за централизованную обработку исключений и преобразование их в соответствующие gRPC-ошибки.

Использование перехватчиков позволяет вынести общие проверки за пределы бизнес-логики и не дублировать их в каждом методе.

# Как система работает целиком

Рассмотрим ситуацию, в которой для получения пользователя установлен лимит в 10 запросов в минуту.

1. Через Writer создаётся ограничение, которое сохраняется в MongoDB.
2. Reader получает новое правило и сохраняет его в памяти.
3. Генератор отправляет в Kafka события о запросах пользователей.
4. Reader получает события и подсчитывает их количество.
5. При превышении лимита в Redis создаётся временная блокировка.
6. При следующем обращении к UserService перехватчик проверяет наличие блокировки и отклоняет запрос.
7. Через 5 минут блокировка автоматически удаляется.

При этом пользователи, которые не превысили установленное ограничение, продолжают работать с сервисом.

# Внутренняя архитектура сервисов

Внутри сервисов используется слоистая архитектура.

Ответственность разделена между несколькими слоями:

- **Controller** — принимает gRPC-запросы, проверяет входные данные и формирует ответы;
- **Service** — содержит бизнес-логику и правила работы системы;
- **Repository** — отвечает за взаимодействие с базами данных;
- **Domain** — содержит основные сущности предметной области.

Также в проекте разделены модели запросов и ответов API, доменные модели и модели базы данных.

Для преобразования моделей используется **Mapperly**, а для проверки входных данных — **FluentValidation**.

Зависимости между компонентами организованы через интерфейсы и **Dependency Injection**. Это позволяет уменьшить связанность классов, заменять отдельные реализации и тестировать бизнес-логику независимо от баз данных.

# Асинхронность и потокобезопасность

Поскольку система одновременно работает с пользовательскими запросами, базами данных и событиями из Kafka, отдельное внимание уделено асинхронной обработке.

В проекте используются:

- `async/await` — для асинхронного выполнения операций;
- `CancellationToken` — для отмены операций;
- `IAsyncEnumerable` — для последовательного получения данных из MongoDB;
- `ConcurrentDictionary` — для потокобезопасного хранения ограничений;
- `SemaphoreSlim` — для защиты общего состояния при подсчёте запросов;
- `IHostedService` и `BackgroundService` — для выполнения фоновых процессов.

Фоновые процессы отвечают за обновление ограничений, получение событий из Kafka и другие операции, которые выполняются независимо от пользовательских запросов.

Для проверки отдельных компонентов и взаимодействия системы написаны модульные и интеграционные тесты с использованием xUnit.
